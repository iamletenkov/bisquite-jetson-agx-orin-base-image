# Образы NVIDIA Jetson

Конвейер от тарболла BSP до готовых образов робота: базовый L4T (классический,
прошиваемый кабелем) плюс слои [bisquite](https://github.com/iamletenkov/bisquite)
поверх него — камеры Sensing GMSL2 и рабочая станция с CUDA, TensorRT и десктопом.

**Плата выбирается переменной `BOARD`**, а не правкой файлов:

```bash
git clone --recurse-submodules <этот репозиторий>
make bsp                    # AGX Orin, JetPack 6.2 / L4T 36.4.3
make BOARD=xavier-agx bsp   # AGX Xavier, JetPack 5.1.x / L4T 35.6.5
make boards                 # какие профили есть
```

Клонировать **обязательно с `--recurse-submodules`**: каталог `scripts/` —
это ссылка внутрь подмодуля `bisquite-extensions`, см. «Откуда берутся
сценарии». Забыл — `git submodule update --init`, и `make` сам об этом скажет.

Цель — **у NVIDIA нет готового qcow2 для L4T**. Там, где для Raspberry Pi или
обычной Ubuntu берут опубликованный образ и накладывают слои, для Jetson образ
приходится **изготавливать**: из BSP, sample rootfs и `jetson-disk-image-creator.sh`.
Этот репозиторий делает изготовление воспроизводимым.

## Что на выходе

| Артефакт | Чем прошивается | Кто делает |
|---|---|---|
| `jetson-orin-bsp.img` | классически, `l4t_initrd_flash.sh` / `dd` | `scripts/08-build-base-image.sh` |
| `jetson-orin-bsp.qcow2` → `jetson-orin-bsp:36.4.3` | `bs device write` | он же, тем же прогоном; в хранилище — `bs image import` |
| `jetson-orin-base:36.4.3` | `bs device write` | `vmfiles/jetson-orin-base.vmfile`: камеры, cloud-init, утилиты, CUDA, TensorRT, GStreamer, OpenCV, PyTorch, jtop |
| `jetson-orin-robot:36.4.3` | `bs device write` | `vmfiles/jetson-orin-robot.vmfile`: GNOME, x11vnc, code-server, Selkies с аппаратным кодированием H.264 (`pixelflux-tegra`), Teleport, обои, btop, Docker |

Классический `.img` и `.qcow2` — **один и тот же диск**, отличаются только
контейнером: второй получается конвертацией первого. Разметка, `PARTUUID`
и загрузочная запись у них совпадают байт в байт.

## Удалённый доступ к роботу — только по петле

`x11vnc`, `code-server` и Selkies слушают `127.0.0.1` и пароля не просят:
к петле дотягивается только тот, кто уже на машине, — у него и так шелл.
Манифест `device/jetson-orin-robot.yml` наружу их **не открывает**, и строки,
которые это делали (`X11VNC_LISTEN=all`, `CODE_SERVER_BIND=0.0.0.0`), в нём
закомментированы.

Отдельно про Selkies: он не публикуется наружу ни одним манифестом записи,
и это не осторожность про конкретный стенд. Без пароля он отдаёт рабочий стол,
буфер обмена, файлы и API команд любому, кто дотянулся до порта, — то есть
равен шеллу. Снаружи ходят через веб-приложение Teleport (его `join` —
последняя команда первой загрузки) или пробросом порта:

```bash
ssh -L 6900:127.0.0.1:6900 <пользователь>@<робот>
```

Аппаратное кодирование H.264 даёт `pixelflux-tegra`: он подменяет pixelflux
внутри AppImage Selkies колесом апстрима с бэкендом Tegra. На живой сессии
1080p@30 — **0.089 ядра** против 0.423 на x264.

## Хост: шаги 01-08 идут и на aarch64, но через эмуляцию

Цепочка двухэтапная, и этапы предъявляют к хосту разные требования.

**Шаги `01`-`08` (изготовление BSP-образа) работают на обеих архитектурах,
но на aarch64 — только с зарегистрированным binfmt.** Хостовый инструментарий
внутри `Linux_for_Tegra` собран NVIDIA под x86 (`tegrarcm_v2` вообще 32-битный
i386), и без эмуляции на aarch64 всё встаёт на первом же его бинаре:

```
flash.sh: line 674: ./tegrarcm_v2: cannot execute binary file: Exec format error
```

Лечится ДВУМЯ пакетами, и второй легко забыть:

```bash
sudo apt-get install -y qemu-user-static binfmt-support
```

`qemu-user-static` сам по себе регистраций НЕ создаёт — их заводит
`binfmt-support` (`update-binfmts`). Проверка:

```bash
update-binfmts --display | grep -A1 qemu-x86_64   # ждём "(enabled)"
```

Проверено на AGX Orin 2026-09-18: после установки обоих пакетов `08` прошёл
целиком на самой плате — `system.img`, `esp.img`, подпись через `tegrabct_v2`
и `tegrasign`, GPT из 15 разделов, на выходе `jetson-orin-bsp.img` 9.46 ГБ
и `jetson-orin-bsp.qcow2` 7.01 ГБ. `virt-inspector` видит Ubuntu 22.04.5 LTS
aarch64.

Плата для этого не нужна: шаги `05`-`07` (прошивка кабелем) — единственные,
кому нужен USB и recovery, а образ изготавливается без них.

**Слои bisquite (`bs image build` по `vmfiles/`) идут только на arm64.** Их
`EXTENSION`, `INSTALL` и `RUN_COMMAND` выполняют код в госте, а libguestfs
не исполняет чужую архитектуру — `bs image validate` отвергает такой VMFILE
до скачивания базы.

Отсюда удобное следствие: на arm64-узле можно пройти всю цепочку целиком,
от BSP до образа робота, не перекладывая qcow2 между машинами.

**На x86_64 binfmt нужен по обратной причине:** `apply_binaries.sh` в шаге `03`
делает chroot в aarch64-дерево. На aarch64-хосте этот chroot нативный, и
проверка binfmt в шаге `03` там пропускается — `qemu-user-static` нативную
архитектуру не регистрирует вовсе.

**libguestfs на L4T требует подготовки.** supermin ищет ядро по шаблону
`vmlinu?-*`, а на L4T оно называется `/boot/Image`. Лечится копированием
`vmlinuz-*-generic` из deb-пакета плюс `depmod`; ставить пакет ядра через
`apt install` нельзя — его постинст зовёт `nv-update-extlinux` и перепишет
`extlinux.conf` вместе с записью `JetsonIO` и оверлеем камер.

## Состав `scripts/`

| Шаг | Что делает | Плата | root |
|---|---|---|---|
| `01-fetch-l4t.sh` | BSP, sample rootfs, два оверлея; сверка SHA1 | нет | нет |
| `02-fetch-camera-drivers.sh` | драйверы Sensing с GitHub | нет | нет |
| `03-prepare-bsp.sh` | распаковка, оверлей QSPI, `apply_binaries.sh`, подмена `libnvisppg.so` | нет | да |
| `04-customize-rootfs.sh` | rootfs: учётка (или `-U` без неё), пакеты, пакет камер в `/opt/sensing` | нет | да |
| `05-generate-images.sh` | генерация образов (`--no-flash`) | **в recovery** | да |
| `06-flash.sh` | заливка платы кабелем — **необратимо** | **в recovery** | да |
| `07-flash-rootfs-ssh.sh` | перезалить только rootfs, если `06` оборвался | **в initrd** | да |
| `08-build-base-image.sh` | `.img` + `.qcow2` для тиражирования на флот | нет | да |
| `09-build-jetson-base.sh` | оркестратор `01`→`02`→`03`→`04 -U`→`08`→`bs image import` | нет | да |
| `10-flash-internal.sh` | выборочно: только загрузчик, либо загрузчик + eMMC | **в recovery** | да |
| `90-install-sdkmanager.sh` | NVIDIA SDK Manager, по желанию | нет | да |

Платозависимого в самих сценариях не осталось: версия L4T со ссылками и
суммами, XML разметки, конфиг QSPI, dts оверлея, пакет камер, цель `flash.sh`
и SKU модуля читаются из окружения, а согласованный набор на плату лежит
в `scripts/boards/<плата>.env`. `make` подставляет профиль сам; руками это

```bash
set -a; . scripts/boards/xavier-agx.env; set +a
sudo -E scripts/09-build-jetson-base.sh -t jetson-xavier-bsp:35.6.5
```

`sudo -E` обязателен — без него sudo вычистит окружение и соберётся Orin.

Разбор каждого шага, включая уже наступленные грабли, —
[`scripts/README.md`](scripts/README.md).

## Что базовый образ про камеры знает, а чего не знает

Различие несущее, и на него легко ошибиться. Базовые скрипты **камеры
не включают**. Шаг `04` кладёт пакет драйверов Sensing в `/opt/sensing`
как файлы и ставит userspace-утилиты (`v4l-utils`); шаг `03` подменяет
`libnvisppg.so` из оверлея камер NVIDIA — это библиотека ISP, а не драйвер
GMSL2. Ни ядро, ни модули, ни DTB-оверлей, ни `extlinux.conf` базовые
скрипты не трогают (проверяется поиском по ним: `boot/Image`, `.ko`,
`JetsonIO`, `dtbo` не встречаются).

Всё, от чего камеры действительно работают, делает **расширение
`sensing-gmsl2-camera`**: заменяет `/boot/Image` ядром Sensing, кладёт
`tegra-camera.ko` и `nvhost-nvcsi-t194.ko`, копирует DTB-оверлей и
дописывает в `extlinux.conf` запись `JetsonIO`, сохраняя прежнюю как
`backup`.

Смысл разделения: базовый образ остаётся общим для всего флота и
камеронезависимым, а слой ложится только на те машины, где адаптер
физически есть. Замена ядра — не то, что стоит нести плате без камер.

`/opt/sensing` при этом наполняют **оба** — и шаг `04`, и расширение, —
и это не недосмотр, а два разных потребителя:

* шаг `04` кладёт пакет для **классического пути**: плату прошили кабелем,
  она стоит на столе, сети у неё может не быть вовсе, а оператору нужен
  `quick_bring_up.sh` под рукой. Довод записан прямо в скрипте;
* расширение кладёт свой экземпляр, потому что обязано работать поверх
  **любой** базы, а не только нашей.

Цена дублирования — 43 МБ (замер пакета `SG8A_AGON_G2Y_A1_…_L4TR36.4.3`),
и на платах без адаптера они лежат мёртвым грузом. Для флота из машин
с камерами это терпимо; если базовый образ понадобится камеронезависимым
строго, убирать надо из `04` — но тогда классический путь теряет офлайн
bring-up, и решать это надо осознанно, а не мимоходом.

## Две половины, и они запускаются на разных машинах

```
станция прошивки (amd64, Ubuntu 22.04)      arm64-хост (сам Jetson)
┌──────────────────────────────────┐        ┌────────────────────────────┐
│ 01 скачать L4T + драйверы камер  │        │ bs image build base        │
│ 02 …                             │        │ bs image build robot       │
│ 03 развернуть BSP                │        └────────────────────────────┘
│ 04 подготовить rootfs (-U)       │                    ▲
│ 08 собрать .img и .qcow2         │────────────────────┘
│ 09 всё перечисленное + import    │   jetson-orin-bsp едет в хранилище
└──────────────────────────────────┘
```

**Перепутать половины нельзя, и это сторожит сам bisquite.** Слои `INSTALL`,
`EXTENSION`, `RUN_COMMAND` и подобные выполняют код **внутри гостя**, а
libguestfs чужую архитектуру не эмулирует — на amd64 такой VMFILE отвергается
до начала сборки. Верное поведение, а не поломка.

Почему станция именно на 22.04: JetPack 6.2 (L4T 36.4.3) фильтрует список
копируемых бинарей буквально как `grep -E "^(jammy|all)"`, а
`ota_make_recovery_img_dtb.sh` зовёт `ssh-keygen -t dsa` — OpenSSH выбросил DSA
в 9.8, и на 24.04 шаг падает. На jammy стоит 8.9, и вызов проходит.

## Быстрый старт

На станции прошивки (или на arm64-узле — шаги 01-08 идут и там):

```bash
make bsp                     # 01→02→03→04→08 плюс регистрация в хранилище bisquite
make BOARD=xavier-agx bsp    # то же под AGX Xavier
```

На Jetson (arm64):

```bash
make images          # base (с --smp/--memsize под PyTorch), затем robot поверх него
```

`make help` печатает все цели с пометкой, где какая запускается, и показывает
выбранную плату. `make boards` — список профилей.

## Загрузчик прошивается один раз на модуль

У AGX Orin загрузчик живёт **в QSPI-NOR на самом модуле**, а не на носителе.
На SSD едут только ESP, ядро, DTB и rootfs. Отсюда два следствия.

> **У AGX Xavier QSPI нет.** Его загрузчик и раздел `esp` лежат во внутренней
> eMMC модуля, и прошивается он вместе с ней (`make BOARD=xavier-agx
> flash-emmc`); `flash-qspi` на этой плате отказывает вслух. Плюс с USB
> Xavier не грузится вовсе — носителем системы может быть только NVMe
> в слоте M.2 Key M. На запись это не влияет: шаг `08` переписывает `root=`
> на `PARTUUID`, поэтому диск пишется в USB-боксе и переставляется в плату.

**Первое: QSPI и rootfs обязаны быть из одного набора.** Плата с JetPack 5
(L4T 35.x) в QSPI не загрузит образ JetPack 6: между ними сменилась вся
загрузочная цепочка. Расхождение в минорной версии внутри JP6 может и
загрузиться, но это состояние NVIDIA не поддерживает — `06-flash.sh` не
случайно обновляет QSPI и загрузочные разделы eMMC одной операцией.

**Второе: кабель нужен ровно один раз.** `make flash` (сценарий 06) пишет QSPI,
разметку и rootfs — это необратимо, отката на прежнюю версию L4T после неё
не остаётся, и сценарий переспрашивает словом «да». Дальше плата обслуживается
только записью носителей, без recovery и без кабеля.

Узнать, что сейчас в QSPI работающей платы: `cat /etc/nv_tegra_release`.

## eMMC как запасная система

Внутренняя eMMC (`mmcblk0`, ~59 ГБ) может нести **базовую систему без
bisquite и cloud-init** — чтобы при отказе основного диска, внешнего или
внутреннего, плата всё равно во что-то загрузилась. Это `make flash-emmc`.

⚠️ **Дерево для eMMC готовится иначе, чем для образа флота, и перепутать
их — значит получить систему, в которую нельзя войти.**

Шаг `04` с флагом `-U` не создаёт учётку вовсе и пароль root не задаёт:
для образа флота это верно, потому что креды приходят из манифеста записи
через cloud-init. Но в eMMC cloud-init не приедет — слои bisquite туда не
применяются, — и войти будет нельзя ни по ssh, ни с консоли.

Поэтому под eMMC дерево готовят с учёткой:

```bash
sudo WORK=/srv/jetson scripts/04-customize-rootfs.sh -u rescue -p <пароль>
make flash-emmc
```

а под образ флота — заново и с `-U` (это делает `make bsp-fresh`).
Два прогона, а не один: шаг `03` необратим, и `04` правит дерево на месте.

Скрипт это проверяет сам: перед заливкой в eMMC он смотрит, есть ли
в `rootfs/etc/passwd` хоть одна учётка с uid ≥ 1000, и отказывается
писать, если её нет. Аварийный носитель, в который не залогиниться, хуже
его отсутствия — он выглядит рабочим ровно до того момента, когда
понадобился.

## Прошивка только QSPI

`make flash-qspi` переписывает **только загрузчик**, не трогая носители.
Это то, что нужно, когда у платы «чужой» JetPack: загрузчик и rootfs
обязаны быть из одного набора.

Используется конфиг `p3737-0000-p3701-0000-qspi.conf` из самого BSP —
внутри у него `NO_ROOTFS=1` и `NO_RECOVERY_IMG=1`, то есть образы rootfs
и recovery не генерируются в принципе. Это путь, документированный NVIDIA
в `tools/kernel_flash/README_initrd_flash.txt`, а не надстройка над общим
конфигом.

⚠️ Обе цели **не прогнаны на железе**: команды собраны по README самого
BSP и по конфигам, которые в нём лежат. Первый прогон делай с монитором,
подключённым к плате.

## Образ привязан к модели платы

Профиль выбирает плату, но **прогнан на железе только AGX Orin Devkit**:
модуль `p3701-0000`, носитель `p3737-0000`, JetPack 6.2. Расширение камер
прямо проверяет наличие `kernel_tegra234-p3737-0000+p3701-0000-nv.dtb`
и отказывается ставиться на другой плате — DTB и оверлей камер там от чужого
железа.

Профиль `xavier-agx` **собран чтением, а не прогоном**. Что в нём известно
точно: ветка `jetson-agx-xavier-devkit` в `jetson-disk-image-creator.sh`
существует (`boardid=2888`, `boardsku` не заполнен — ровно тот же дефект, что
у AGX Orin, и его чинит тот же патч шага `08`), `flash_l4t_t194_nvme.xml`
в BSP лежит, ссылки и суммы R35.6.5 сверены с `release_sha_hashes.txt`
NVIDIA. Что неизвестно: **SKU модуля** — на пустом шаг `08` отказывает вслух,
потому что угаданный даёт образ под чужое железо. Значение печатает любой
прогон `flash.sh` с платой в recovery:

```
Board ID(2888) version(400) sku(0001) revision(D.0)
```

Слоёв bisquite (`vmfiles/jetson-xavier-*.vmfile`) под Xavier ещё нет —
`make BOARD=xavier-agx base` отказывает и говорит об этом. Для Orin NX,
Orin Nano или другого SKU AGX нужен свой профиль и свой прогон.

## Камеры

Адаптер Sensing **SG8A-AGON-G2Y-A1**, восемь камер GMSL2. Слой заменяет ядро,
кладёт модули и DTB-оверлей и дописывает в `extlinux.conf` запись `JetsonIO`,
сохраняя прежнюю как `backup` — откат выбирается в загрузочном меню.

Работает **только YUV422**; пакет с `_YUV_` в имени на этой камере не
работает, нужен `GMSL2x8`. Номер отвода кабеля не равен номеру порта в софте —
разбор в [`scripts/README.md`](scripts/README.md).

`quick_bring_up.sh` слой намеренно **не** вызывает: выбор модели камеры и
номера порта известен только на конкретной сборке адаптера, и автоматизировать
его значило бы дать ложное чувство готовности. Пакет целиком лежит
в `/opt/sensing`.

## Первая загрузка не требует сети

Свойство профиля, за которым надо следить при добавлении слоёв: расширения
с фазой `firstboot` здесь только доводят настройку до пользователя, которого
создаёт cloud-init, и ничего не скачивают. Поэтому браузер — Firefox `.deb`
из APT-репозитория Mozilla, поставленный на сборке в `jetson-orin-base`
(расширение `firefox`): штатные `firefox` и `chromium-browser` на jammy —
переходники на snap, который пришлось бы доустанавливать на первой загрузке.

Добавляешь слой — проверь его `configure.sh`: иначе свойство потеряется молча,
и узнается это у робота в поле.

## Запись на носитель

Пример манифеста — [`device/jetson-orin-robot.yml`](device/jetson-orin-robot.yml).
Секреты в нём замазаны `********`, **свой держи вне git**.

Главное, что легко сделать неверно: имена сетевых интерфейсов. На AGX Orin это
`eno1` и `wlP1p1s0`, а **не** `eth0`/`wlan0`. Поле `name` обязательное,
wildcard не поддерживает, и вписанное мимо имя даёт молчаливый отказ — линк
есть, адреса нет.

## Связь с другими репозиториями

| Репозиторий | Что берёт отсюда / отдаёт сюда |
|---|---|
| [bisquite](https://github.com/iamletenkov/bisquite) | сам инструмент `bs`: сборка VMFILE, хранилище, запись на носители |
| [bisquite-extensions](https://github.com/iamletenkov/bisquite-extensions) | расширения, на которые ссылаются VMFILE. Базовый: `nocloud-cidata`, `sensing-gmsl2-camera`, `cuda-toolkit`, `tensorrt`, `l4t-gstreamer`, `l4t-opencv`, `l4t-pytorch`, `jetson-stats`, `firefox`, `l4t-boot-verify`. Робот: `btop`, `gnome`, `x11vnc`, `code-server`, `wallpaper`, `docker`, `selkies`, `pixelflux-tegra`, `teleport-agent` |

### Откуда берутся сценарии

`scripts/` — **символическая ссылка** в подмодуль, на
`bisquite-extensions/extensions/debian/nvidia-jetpack/scripts`. Источник один,
и он там же, откуда сценарии уезжают в образ станции прошивки
(`/opt/nvidia-jetpack`).

Так было не всегда: копии жили здесь и в расширении, README расширения сам
предупреждал «свести к одному источнику до того, как они разойдутся» — и они
разошлись **в обе стороны**. Здесь появился `10-flash-internal.sh`, которого
не было в расширении; в расширении — заметка про `binfmt-support` на aarch64,
которой не было здесь. Обе правки теперь в одном дереве.

Практическое следствие: правка сценария — это коммит **в bisquite-extensions**
и обновление указателя подмодуля здесь, а не правка файла на месте.
