# Образы NVIDIA Jetson

Репозиторий **скачивает и готовит** образы Jetson из BSP NVIDIA и упаковывает их
в вид, который использует [bisquite](https://github.com/iamletenkov/bisquite):
qcow2-слой для `bs device write` плюс пакет, которым по USB прошивается
загрузчик той же пары «плата × релиз L4T». Всё.

Слоёв bisquite здесь больше нет. VMFILE и манифесты записи, которые раньше
жили в `vmfiles/` и `device/`, переехали в сам bisquite —
`bisquite/examples/build/jetson/` и `bisquite/examples/device/` — и версионируются
вместе с инструментом, который их применяет. У NVIDIA нет готового qcow2 для
L4T: там, где для Raspberry Pi или обычной Ubuntu берут опубликованный образ,
для Jetson его приходится **изготавливать** из тарболла BSP, sample rootfs
и `jetson-disk-image-creator.sh`. Этот репозиторий делает изготовление
воспроизводимым; накладывание слоёв bisquite — отдельная, следующая работа,
и она в другом репозитории.

## Сборочный узел arm64

`tools/provision-arm-builder.sh` и `tools/cleanup-arm-builder.sh` отсюда
уехали вместе с `vmfiles/` и `device/` — по той же причине. Они снаряжают
сам Jetson как arm64-узел для сборки VMFILE-слоёв bisquite (`bs image
build`), а это забота bisquite, не образов. Переехали в bisquite как
`tools/arm64-builder/provision.sh` и `tools/arm64-builder/cleanup.sh`.

Там системные зависимости, Python 3.14 и venv уже даёт одна цель
`make dev-uv`; эти скрипты добавляют то, чего она не делает: починку
supermin под ядро L4T (ядро Ubuntu распаковывается `dpkg -x`, никогда
`apt install` — его постинст переписал бы `extlinux.conf`), проверку
членства в группе `kvm` и настройку источника расширений. Подробности —
в самом bisquite.

## Nano пока не поддерживается

Этот репозиторий Jetson Nano не собирает, и это не недосмотр. Развёрнутого
дерева BSP L4T R32 для Nano нет; пакет загрузчика для него не измерен;
у R32 `jetson-disk-image-creator.sh` другой интерфейс — нет `-d`, а `-r`
(ревизия) обязателен, и профиль пары сюда просто так не ляжет. Парк Nano
сейчас работает на образе Q-engineering (focal) — эта цепочка не отсюда,
она уже в bisquite, `examples/build/jetson/nano/`.

## Быстрый старт

```bash
git clone --recurse-submodules <этот репозиторий>
cd bisquite-jetson-base-image
make list                                       # объявленные платы и релизы
make build jetson=agx-xavier l4t=35.6.5         # → out/agx-xavier-35.6.5/
make flash jetson=agx-xavier l4t=35.6.5 to=bootloader   # НЕОБРАТИМО, нужна плата
make matrix                                     # таблица «плата × релиз × статус»
```

Клонировать **обязательно с `--recurse-submodules`**: каталог `scripts/` — это
символическая ссылка внутрь подмодуля `bisquite-extensions`, см. раздел
«Откуда берутся сценарии» в конце. Забыл — `git submodule update --init`,
и любая цель `make` сама скажет об этом (`check-submodule`).

`make help` печатает все цели с однострочным описанием.

## Что отдаёт `make build`

```
out/<плата>-<релиз>/
    system.qcow2         базовый слой для bisquite
    bootloader.tar.gz    пакет прошивки загрузчика по USB, без дерева BSP
    manifest.json        пара, значения платы, версия BSP, sha256 обоих файлов
```

Оба файла рождаются из одного дерева за один прогон — пара неразделима
по построению: `system.qcow2` и `bootloader.tar.gz` из разных сборок никогда
не гарантированно совместимы, а из одной — всегда.

Внутрь `system.qcow2` вдобавок кладётся второй, внутренний манифест —
`/opt/l4t-boot-firmware/manifest.json`. Он не копия внешнего, а самостоятельное
опознание пары: по содержимому образа, даже через год, можно однозначно найти
его загрузчик, не полагаясь на имя файла или память о том, как образ собирался.

| | Внешний `out/<пара>/manifest.json` | Внутренний `/opt/l4t-boot-firmware/manifest.json` |
|---|---|---|
| значения платы, версия BSP, SHA1 тарболла BSP | да | да |
| sha256 **двоичных файлов загрузчика** (подписанные образы из `bootloader/signed/`) | да | да |
| sha256 `bootloader.tar.gz` и `system.qcow2` | да | **нет** |

Хеш архива во внутренний манифест положить **нельзя**, и причин две. У Xavier
полный пакет содержит rootfs — манифест внутри этого же rootfs должен был бы
знать хеш архива, в который сам входит: круг. И `tar.gz` недетерминирован —
метки времени дают новый хеш при каждой сборке одной и той же пары, поэтому
такой хеш не был бы опознанием, а только шумел бы. Хеши двоичных файлов
загрузчика обоих недостатков лишены: они определяются деревом BSP и
значениями платы, а не упаковкой. Сверка «этот архив от этого образа» идёт
по ним — распаковать архив, посчитать суммы файлов загрузчика, сравнить
с внутренним манифестом.

## Цели

| Цель | Нужна плата | Обратимо |
|---|---|---|
| `make build` | нет | да — результат лежит в `out/`, ничего не тронуто на диске хоста, кроме рабочего дерева BSP |
| `make flash … to=…` | да | **нет** — пишет загрузчик и/или носитель, отката нет |
| `make verify` | нет | да — тарболл BSP читается потоком, на диск не кладётся |
| `make verify-all` | нет | да — то же по всем совместимым парам |
| `make matrix` | нет | да — только читает `verified/` и `status.tsv` |
| `make list` | нет | да |
| `make check` | нет | да — синтаксис, shellcheck, тесты |

Целей `clean` и `boot-images` нет: дерево пары сносится руками (шаг 03
сам печатает нужную команду), а генерация образов для прошивки — часть
`build`. Отдельной цели `build-fresh` тоже нет — то же самое делает
`fresh=1`.

## Пакет загрузчика

`l4t_initrd_flash.sh --no-flash --massflash 1` в **offline-режиме**: значения,
которые обычно читаются из EEPROM платы, подаются переменными
`BOARDID`/`FAB`/`BOARDSKU`/`BOARDREV`. Режим документирован в
`tools/kernel_flash/README_initrd_flash.txt` самого BSP. Получается
самодостаточный архив, который шьёт плату `--flash-only` на любой машине
с подходящей ОС — дерево BSP для прошивки больше не нужно.

Что именно попадает в пакет, решает поколение платы, а не наш вкус:

| Плата | Где загрузчик | Пакет | Замер 2026-09-18 |
|---|---|---|---|
| AGX Orin | QSPI модуля | `--qspi-only` | **2,5 ГБ** (сами образы QSPI — 12 МБ) |
| AGX Xavier | внутренняя eMMC, QSPI нет | полный: загрузчик + rootfs на eMMC | **4,5 ГБ** |

**`--qspi-only` не делает пакет лёгким.** Он ограничивает то, ЧТО
прошивается, но не то, что пакуется: massflash копирует в архив весь
`rootfs/` целиком (7,1 ГБ в распакованном виде у Orin, вплоть до пакетов
Python), хотя сам загрузчик Orin — это 12 МБ подписанных образов
в `tools/kernel_flash/images/` плюс ещё около 160 МБ каталога `bootloader/`.
Скрипты прошивки на этом rootfs собирают флеш-initrd, которым плата
грузится по USB во время заливки, и какая часть rootfs им нужна на самом
деле, а какая балласт, неизвестно — выяснить это можно только реальной
заливкой. Поэтому пакеты берутся такими, какими их собирает NVIDIA, без
вырезания: сломанная прошивка загрузчика — ровно та ошибка, которую нельзя
себе позволить. Облегчение пакета — отдельная задача, и только после первой
успешной заливки на железе.

У Xavier отдельной кнопки «только загрузчик» нет (`-p "--no-systemimg"`
систему не отсекает, `-k` берёт по одному разделу за прогон при десятке
загрузочных), поэтому пакет там полный. Отсюда следствие, которое надо
помнить: **у Xavier `make flash … to=bootloader` пишет и rootfs во
внутреннюю eMMC**, не только загрузчик. Для платы, которая грузится
с NVMe, это безвредно, но eMMC после такой прошивки не пуста и учётки
в этом rootfs нет — креды на образ флота приходят из cloud-init при записи
носителя, а на eMMC cloud-init не приезжает. Входить в систему на eMMC
нечем: она там как следствие формата пакета, а не как запасная система.

## Значения платы

Измерены на живых платах, а не взяты из таблиц NVIDIA:

| | BOARDID | FAB | BOARDSKU | BOARDREV | источник |
|---|---|---|---|---|---|
| AGX Xavier | 2888 | 400 | 0001 | J.0 | TNSPEC, записанный при вендорской прошивке |
| AGX Orin | 3701 | 500 | 0000 | J.0 | EEPROM `699-13701-0000-500 J.0` |

Три ловушки, каждая уже поймана:

1. **Таблица в README NVIDIA — примеры, а не справочник.** Для AGX Xavier
   16 ГБ там указан `H.0`, у нашей платы — `J.0`; для AGX Orin там `TS4 A.0`,
   у нашей — `500 J.0`.
2. **TNSPEC на платах, прошитых нашими образами, недостоверен.** У Orin там
   `3701-default-0000--…` — это записал наш же сборщик
   (`BOARD_REVISION=default`), а не плата. Источник правды — EEPROM
   (`/sys/bus/i2c/devices/0-0050/eeprom`) и `/proc/device-tree`.
3. **Пакет привязан к аппаратной ревизии, а не к модели.** README massflash
   прямо требует «make sure all devices are in exactly the same hardware
   revision». Для парка это значит: пакет собирается на ревизию, и ревизия
   обязана лежать в манифесте — плата другой ревизии той же модели получит
   образ под чужое железо.

## Парк

`tools/fleet-firmware.sh report hosts.txt` — инвентаризация: версия системы,
версия прошивки, TNSPEC, значения EEPROM, состояние слотов. **Только читает**,
ничего не меняет (режима `apply` пока нет — приведение парка к одной версии
загрузчика вручную, по правилам ниже, отдельная задача).

Правила, по которым парк внутри одной модели приводится к одной версии
загрузчика — они не про инструмент, а про то, что позволяет и не позволяет
сама платформа:

- **Версия прошивки ≠ версия системы.** Спрашивать надо у прошивки
  (`l4t_payload_updater_t210 -v` / `nvbootctrl dump-slots-info`), а не у
  `/etc/nv_tegra_release` — они расходятся, и это нормально.
- **Только вверх.** Anti-rollback не даёт опустить версию прошивки ничем,
  кроме полной перепрошивки кабелем.
- **Внутри поколения — без кабеля**, готовым payload с целевого образа;
  **между поколениями — только кабель** (`make flash … to=bootloader`):
  старая прошивка не грузит новую систему.
- **Проверка обязательна.** Несовпадение спеки капсулы у некоторых плат —
  тихий отказ: плата как ни в чём не бывало продолжает грузиться на старой
  прошивке, и без явной проверки статуса обновления это не видно вообще.

## Хост прошивки

Не любая Ubuntu годится: `l4t_initrd_flash.sh` и связанные с ним шаги
чувствительны к версии хоста. Колонка `ХОСТ-ПРОШИВКИ` в `make matrix` берёт
это значение из профиля релиза:

| Релиз L4T | Годные хосты |
|---|---|
| 35.6.5 | 18.04, 20.04 |
| 36.4.3 | 20.04, 22.04 |
| 39.2 | 24.04 |

## Прошивка пакетом не проверена на железе

Цель `make flash … to=bootloader` (шаг `14-flash-bootloader.sh`) собрана
по README самого BSP и по конфигам massflash, но ни разу не прогонялась на
реальной плате в recovery. Первый прогон делай с монитором, подключённым
к плате, и будь готов, что README NVIDIA в паре мест расходится с
поведением на живом железе (см. «Значения платы» выше).

## Откуда берутся сценарии

`scripts/` — **символическая ссылка** в подмодуль `bisquite-extensions`, на
`extensions/debian/nvidia-jetpack/scripts`. Источник один, и он тот же,
откуда сценарии уезжают в образ станции прошивки (`/opt/nvidia-jetpack`).

Так было не всегда: копии жили здесь и в расширении одновременно, и они
разошлись **в обе стороны** — в этом репозитории появлялись правки,
которых не было в расширении, и наоборот. Держать один источник и ссылку
на него — единственный способ не наступать на это снова. Разбор каждого
шага, включая уже наступленные грабли, — в `scripts/README.md` (внутри
подмодуля).

Адрес подмодуля в `.gitmodules` — **https, а не ssh**, и это не небрежность:
станция прошивки и сборочные узлы ключей GitHub не имеют, а читать подмодуль
им надо. Пушить в сам подмодуль с этих машин не требуется; кому нужен push
по ssh — ставит `url.insteadOf` у себя, в общий `.gitmodules` это не идёт.
Практическое следствие то же, что и раньше: правка сценария — это коммит
**в bisquite-extensions** и обновление указателя подмодуля здесь, а не
правка файла на месте.
